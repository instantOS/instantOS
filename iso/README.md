# instantOS iso build

## What this is

A fork of the releng archiso profile. 

## How to update this

Manually copy `/usr/share/archiso/configs/releng/` here. 
Then use a git client to figure out what changed upstream, and manually revert
the stuff which got overwritten even though instantOS should have it changed.
Anything interesting which changed upstream will stand out in the git diff. 

The live-image customizations belong in `overlay/`, which is their single source
of truth. `build.sh` copies the upstream-derived `releng/` profile to its build
directory and then applies `overlay/` to that temporary copy. Do not duplicate
overlay files under `releng/airootfs/`. `update.sh` only refreshes the upstream
releng base; it does not modify or copy the overlay.

The live image version in `/etc/instantos/version` is generated at build time
from `SOURCE_DATE_EPOCH`, or from the current time when it is unset. The same
UTC date is used by the archiso profile for its ISO version and label.

The live user is configured for greetd autologin and its default instantOS
dotfiles repository is cloned and applied with `ins dot` by `instantos-setup`.
The welcome app starts via XDG autostart and launches the TUI installer in a
terminal.

At live-session startup, `liveautostart` refreshes the package-managed `ins`
package before Welcome and the installer applet are launched. If the machine is
offline or the refresh fails, the version bundled in the ISO remains available.

## Build-time inputs and verification

`build.sh` fetches the dotfiles, instantTOOLS, and liveutils repositories before
starting `mkarchiso`. Their resolved commits are recorded in
`/usr/share/instantos/build-sources.env`. The package hook configures the live
system exclusively from those bundled sources, so it does not depend on DNS or
network access inside the temporary airootfs chroot.

The hook writes `/opt/instantos/.setup-done` only after all customizations have
been applied and checked. Failures are recorded in
`/opt/instantos/.setup-failed` for diagnostics. Pacman continues running its
remaining post-transaction hooks after a hook failure, so `build.sh` does not
trust the package transaction alone. After `mkarchiso` returns, `verify.sh`
extracts the root squashfs from the finished ISO and verifies the marker, live-user
dotfiles, instantTOOLS installation, login configuration, source revisions,
and removal of the build-only package hook. A missing or incomplete instantOS
customization therefore fails the entire ISO build.

Set `DOTFILES_REF`, `INSTANTTOOLS_REF`, or `LIVEUTILS_REF` to build from a
specific branch, tag, or commit. Their corresponding `*_BRANCH` variables
control the branch retained in the bundled Git checkout and default to `main`.

## Live shell and boot appearance

Before `mkarchiso`, `prepare-sheldon.sh` resolves the plugins pinned by the
bundled dotfiles and relocates their lock file to the live user's paths.
The build host needs `sheldon` (installed automatically when missing) and
Python 3. `instantos-setup` copies the plugin sources into the live home and
runs the same interactive zsh initialization as the installer, generating
Sheldon's source and compiled caches without downloading in the chroot.
Image verification requires these caches.

The BIOS Syslinux menu uses a flat Catppuccin Mocha background, no logo,
and a menu width and offset that fit its 80-column screen. UEFI keeps
systemd-boot's plain menu. Normal boot entries enable `quiet splash`;
speech entries keep verbose boot output. The live initramfs includes KMS
and Plymouth, using the instantOS theme with no display delay.

Releng was refreshed from the installed archiso 92 profile. Downstream
branding, package repositories, signing initialization, KMS, initramfs preset,
and file permissions were reapplied. Upstream's architecture-specific Memtest
EFI filenames, ARM profile inputs, and current profile options were retained.

## Offline-install variant

`just build-iso-offline` (or `iso/build.sh --offline`) produces a second
artifact, `instantos-<version>-offline.iso`, which can install a full system
with no network at all. The design and its evidence live in
`../offlineiso.md`; the short version:

- `offline/mk-package-list.sh` derives the package manifest from the
  installer itself: it dry-runs one `ins arch exec` questions file per
  wizard plan variant (kernels, desktops, display managers, booleans,
  locales, hardware shapes) and unions the result into
  `offline/packages.list`, which is committed and regenerated by the build.
  Without a usable `ins` binary the build falls back to the committed list.
- `offline/mk-bundle.sh` downloads the manifest (plus its dependency
  closure) with a scratch pacman config, stages the archives into
  `core|extra|multilib|instant/os/x86_64`, runs `repo-add` per repository,
  snapshots mirror-region data (`offline/mk-region-data.sh`), and records
  the manifest inside the bundle.
- After `mkarchiso`, the bundle is injected at the ISO root with
  `xorriso -boot_image any replay -map` — not inside `airootfs.sfs`, which
  cannot hold a multi-GiB single file (ISO9660 limit). The offline build
  also merges `overlay-offline/` (a `file://`-first mirrorlist) and adds
  the bundle server to the `[instant]` repo in the profile's pacman.conf.
- `verify.sh ISO --offline` additionally asserts bundle completeness
  (manifest ⊆ staged packages), repository databases, signatures for the
  signed repositories, region snapshot presence, the 4 GiB single-file
  safety margin, and the `file://`-first mirrorlist in the live image.

The installer (`ins`) detects the bundle at `/run/archiso/bootmnt/offline-repo`
and switches to opportunistic offline mode on its own; nothing about the
online ISO or the online install path changes. See offlineiso.md for the
design and installation testing.

## Publishing releases

The release workflow builds the live and offline ISOs on separate runners, using
one shared build timestamp. Both verified ISOs are transferred to a publishing
job through temporary GitHub Actions artifacts. Pushes to `release`, and manual
runs with `create_release` enabled, publish them to the public
[GitLab package-hosting project](https://gitlab.com/instantos/instantos-releases).
GitHub releases contain the release notes, SHA256 hashes, GitLab download
links, and a small `build.json` attachment. ISOs are hosted only in GitLab’s
Package Registry; no GitLab releases are created.

Repository settings under **Secrets and variables → Actions**:

- Secret **`GITLAB_TOKEN`**: a fine-grained personal access token scoped to the
  release project with **Project: Read** and **Package: Read and Create** permissions.
  Release and Delete permissions are not needed.
  A legacy personal access token with `api` scope also works; a deploy token
  is not supported by the publisher’s project and package-metadata API calls.
  Renew the token before its expiry date.
- Variable **`GITLAB_PROJECT_ID`**: `89059216`.

The GitLab project must be public, have its package registry enabled, and allow
anonymous package downloads. No GitLab repository initialization, GitLab CI
runners or paid subscription are needed.

`iso/publish-gitlab.py` uploads the two ISOs, generated SHA256 files, and
`build.json` as a generic package named `instantos-iso`, versioned as
`build-<workflow run number>-<attempt>`. It checks both ISO sizes against the
5 GiB per-file limit before any upload, then verifies the stored sizes and
SHA256 hashes through the GitLab API and checks anonymous download access.
Only after all checks succeed does it write local release notes and `build.json`
for `iso/publish-github.py`. That script attaches the manifest to a draft GitHub
release, then publishes it as latest. A failed build or upload leaves the
previous latest GitHub release intact. Tags include both the workflow run number
and attempt: `v<date>-<run>-<attempt>`.

Download discovery:

- [Latest release and download links](https://github.com/instantOS/instantOS/releases/latest)
- [Latest build metadata](https://github.com/instantOS/instantOS/releases/latest/download/build.json)

The metadata contains `live.url`, `offline.url`, and their `sha256Url` fields,
which point directly to immutable, build-specific GitLab package files.

Publication is serialized with the workflow's `gitlab-iso-release` concurrency
group. Older workflow runs or attempts cannot replace a newer published GitHub
release. Previous GitHub releases and GitLab packages are kept; the publisher
never deletes them. Retrying the same
build skips files whose stored sizes and SHA256 hashes match and uploads only
missing files. Conflicting or duplicate files require a new build attempt,
which GitHub Actions reruns provide automatically. Incomplete uploads are kept
and can be removed manually if desired.

The website fetches the latest GitHub `build.json` during its build and uses its
verified package URLs, checksums, version, and sizes. If fetching fails, cached
package links remain valid because old builds are retained; a fresh site build
falls back to the GitHub release page. Rebuild the website to pick up a new release.

The previous SourceForge publisher and its tests remain available for historical
reference, but the workflow no longer uploads there or needs SourceForge secrets.
Existing SourceForge files are not changed by this migration.
